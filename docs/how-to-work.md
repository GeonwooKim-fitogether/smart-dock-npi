# 사용 가이드 — GitHub 에서 NPI 일하는 법

> **한 줄 요지:** **Fitstack NPI 태스크 하나는 GitHub 이슈 하나**이고, **단계는 마일스톤**이다. 어떤 태스크와 단계가 깔리는지는 프로젝트 등급(A·B·C)이 정한다. 팀원은 브라우저에서 내 이슈를 찾아 진행을 댓글로 남기고, 끝나면 근거를 달아 닫는다. 한 단계의 이슈가 모두 닫히면 PM 이 근거를 Fitstack 게이트에 올린다. **단계 통과(Phase Review)와 게이트 승인은 Fitstack 에서만 한다.** GitHub 에는 심사 이슈가 없다.

이 가이드는 [로드맵](roadmap.md) 2단계(GitHub 에 깔기)가 끝난 뒤를 전제로 한다. 그 전이라면 Issues 탭에 아래 이슈들이 아직 없다. 도구별 역할과 정보마다의 정본 자리는 [운영 틀](working-model.md)에 있다.

## Fitstack 의 무엇이 GitHub 의 어디에 있나

| Fitstack NPI | GitHub | 어디서 보나 |
|---|---|---|
| 단계 (게이트) | 마일스톤 `1. Concept`, `2. Planning`, `3. Development`, `4. Release to Manufacturing`, `5. Launch`. 등급이 거치는 단계만 만든다(아래 표) | Issues 탭 → Milestones |
| NPI 태스크 (A 34 · B 16 · C 5) | 태스크 하나에 이슈 하나. 제목은 `[태스크 번호] 제목`, 라벨은 `NPI 태스크` | Issues 탭, 각 마일스톤 화면 |
| 담당 역할 (7종) | `역할:PM`, `역할:HW`, `역할:FW`, `역할:ME`, `역할:QA`, `역할:PROD`, `역할:SCM` 라벨 | 이슈 오른쪽의 Labels |
| 인증이 필요할 때만 깔리는 태스크 | `[5] 인증 계획 확정`, `[16] 인증서 등록`. 본문 표에 `해당 조건: 인증시` 가 붙는다 | 각 이슈의 본문 |
| 단계 통과 (Phase Review), 게이트 승인 | **GitHub 에는 없다.** Fitstack 에서만 한다 | Fitstack |
| 83개 태스크 라이브러리 | `npi/task-library.csv`. 자동으로 깔지 않는다. 필요한 것만 골라 이슈 양식으로 더한다 | 저장소의 `npi/` |
| 증거·산출물 | 이슈 댓글의 링크와 첨부 파일, `exports/` 의 PDF. 같은 파일을 Fitstack 에 보관한다 | 각 이슈 |
| 공식 기록 | Fitstack | Fitstack |

등급마다 거치는 단계와 깔리는 이슈 수는 아래와 같다. 마일스톤 앞 번호는 등급과 관계없는 고정 순번이라, B 와 C 에서는 번호가 건너뛰어 보인다.

| 등급 | 마일스톤 | 이슈 |
|---|---|---|
| `NPI-A` 신규 플랫폼 | 1 · 2 · 3 · 4 · 5 | 34 |
| `NPI-B` 파생 개발 | 1 · 3 · 4 | 16 |
| `NPI-C` 변형 SKU | 3 · 4 | 5 |

태스크의 원래 단계가 그 등급에 없으면, 그 태스크는 등급의 첫 단계로 내려온다. Fitstack 과 같은 규칙이다. 예를 들어 `NPI-B` 에서 `[5] 인증 계획 확정`(원래 Planning)은 `1. Concept` 에 놓이고, `NPI-C` 에서 `[3] 대상 제품 연결`은 `3. Development` 에 놓인다. 이슈 수는 인증이 필요한 기준이며, 인증이 필요 없으면 `[5]`·`[16]` 을 닫아 A 32건, B 14건이 된다.

기준의 원본은 `npi/npi.json`(단계·등급·역할)과 `npi/tasks.csv`(태스크 34개와 등급별 포함 여부) 두 파일이다. GitHub 의 이슈는 이 두 파일로 만든 사본이므로, 기준이 바뀌면 이슈보다 이 파일을 먼저 고친다. `tasks.csv` 를 GitHub 에서 열면 검색할 수 있는 표로 보인다.

## 팀원 — 매일 하는 일

git 을 몰라도 되고, 브라우저만 있으면 된다.

1. **내 할 일 찾기.** 저장소의 Issues 탭 검색창에 `is:open assignee:@me` 를 넣는다. 아직 담당자가 정해지지 않았으면 `is:open label:"역할:HW"` 처럼 내 역할 라벨로 찾는다.
2. **진행 남기기.** 이슈에 댓글을 단다. 시험 결과 파일이나 사진은 댓글 창에 끌어다 놓으면 올라간다.
3. **끝내기.** 산출물과 근거의 링크를 댓글로 남기고 **Close issue** 를 누른다. 이 프로젝트에 해당하지 않는 태스크라면 버튼 옆 화살표에서 **Close as not planned** 를 고르고, 이유를 댓글로 한 줄 남긴다.
4. **등급별 태스크에 없는 일이 생기면** New issue 에서 **NPI 태스크 (표준 외 추가)** 양식을 고른다. 83개 라이브러리에서 고른 태스크도 이 양식으로 더한다. 만든 뒤 오른쪽에서 Milestone(단계)과 역할 라벨을 고른다.
5. **논의할 거리(안건)는 지금처럼** 양식 없는 빈 이슈로 연다. 안건은 태스크가 아니므로 `NPI 태스크` 라벨을 붙이지 않는다.

**하지 않을 것이 둘 있다.** 첫째, 이슈 제목 앞의 `[태스크 번호]` 는 지우거나 바꾸지 않는다. 스크립트를 다시 돌릴 때 그 번호로 같은 태스크를 알아보고, 나중에 Fitstack 과 짝지을 때도 그 번호가 열쇠이기 때문이다. 번호 뒤의 제목은 고쳐도 된다. 둘째, 직접 만드는 이슈의 제목을 `[숫자]` 로 시작하지 않는다. 라이브러리 번호를 그대로 쓰면 같은 번호의 Fitstack 태스크로 오인되어, 스크립트가 그 태스크를 이미 있는 것으로 보고 건너뛴다.

## PM — 처음 한 번: 태스크를 GitHub 에 깐다

**필요한 것.** Windows PC 에 Python 3 와 GitHub CLI(`gh`, GitHub 를 명령으로 다루는 공식 도구)가 있어야 하고, 이 저장소에 Write 이상의 권한이 있어야 한다. `gh` 가 없으면 PowerShell 에서 `winget install --id GitHub.cli` 로 설치한 뒤, 새 PowerShell 창을 열어 `gh auth login` 으로 로그인한다.

**순서.** PowerShell 을 열고 저장소 폴더에서 아래를 차례로 실행한다. 등급이 다르면 `NPI-A` 자리에 `NPI-B` 나 `NPI-C` 를 쓴다.

```powershell
cd C:\Users\<사용자>\Dev\smart-dock-npi

# 1) 미리 보기 — GitHub 를 읽지도 쓰지도 않고, 실행할 gh 명령을 파일로 저장한다
python npi\npi_github.py --grade NPI-A --out $env:TEMP\npi-plan.txt
notepad $env:TEMP\npi-plan.txt

# 2) 실제로 만들기 — 저장소 이름을 직접 적는다
python npi\npi_github.py --grade NPI-A --apply GeonwooKim-fitogether/smart-dock-npi
```

- **미리 보기는 화면 마지막 줄부터 본다.** 만들 라벨·마일스톤·이슈의 개수가 한 줄로 나온다. `NPI-A` 면 라벨 8개, 마일스톤 5개, 이슈 34개다. 기준 데이터에 빈 곳이 있으면 그 목록이 이어서 나오고, 빈 곳이 하나라도 있으면 실제 실행은 거부된다.
- **미리 보기를 파일로 받을 때는 `>` 대신 `--out` 을 쓴다.** PowerShell 의 `>` 는 한글을 깨뜨린다.
- **실제 실행은 몇 분 걸린다.** GitHub 이 권하는 대로 하나를 만들 때마다 1초씩 쉰다. 화면에 "만듦:" 과 이슈 주소가 한 줄씩 찍힌다.
- **중간에 끊기면 같은 명령을 다시 돌린다.** 이미 있는 마일스톤과 이슈는 "건너뜀"으로 넘어가고 남은 것만 만든다.
- **실행이 끝나면** Issues 탭 → Milestones 에 등급의 단계별 마일스톤이 보이고, 각 마일스톤 안에 그 단계의 태스크 이슈가 있다.
- **인증이 필요 없는 프로젝트라면** `[5] 인증 계획 확정` 과 `[16] 인증서 등록` 을 Close as not planned 로 닫는다.
- **기존 안건 이슈(#2~#8)는** 이슈마다 오른쪽 Milestone 에서 `1. Concept` 을 고른다. 여러 개를 한 번에 하려면 Issues 목록에서 체크한 뒤 위쪽의 Milestone 메뉴를 쓴다.
- **마일스톤 마감일은 스크립트가 넣지 않는다.** Milestones 화면에서 각 마일스톤의 Edit 를 눌러 넣는다.

## PM — 매주 하는 일

- **진행 보기.** Issues 탭 → Milestones 를 연다. 마일스톤마다 닫힌 이슈의 비율이 막대로 나오고, 마일스톤을 누르면 남은 이슈가 나온다.
- **담당자 없는 태스크 찾기.** 검색창에 `is:open label:"NPI 태스크" no:assignee` 를 넣는다.
- **미팅 안건.** 지금처럼 열린 안건 이슈가 곧 안건이다([README](../README.md) 의 "미팅 한 번의 흐름").

## 단계 끝 — Fitstack 에서 게이트를 넘긴다

GitHub 에는 심사 이슈가 없다. 단계 통과(Phase Review)와 게이트 승인은 Fitstack 에서만 한다. GitHub 쪽에서 하는 일은 근거를 모아 넘기는 것까지다.

1. 그 단계 마일스톤의 막대가 100% 인지 본다. 해당 없는 태스크도 Close as not planned 로 닫혀 있어야 한다.
2. 이슈마다 남은 근거(댓글의 링크, `exports/` 의 PDF, 결정 기록)를 Fitstack 의 같은 번호 태스크와 그 단계 게이트에 올린다. 확정본 PDF 는 `exports/` 에 두고, 같은 파일을 Fitstack 에 보관한다.
3. Fitstack 에서 Phase Review 를 승인받아 게이트를 넘긴다.
4. 통과하면 GitHub 의 그 마일스톤을 Milestones 화면에서 **Close** 한다. 열린 마일스톤 목록에는 진행 중인 단계만 남는다.

통과하지 못하면 보완할 일을 **NPI 태스크 (표준 외 추가)** 로 만들어 같은 마일스톤에 넣는다.

## 기준이 바뀌면

`npi/npi.json` 이나 `npi/tasks.csv` 를 고치는 PR 을 올리고, 머지한 뒤 PM 이 같은 명령을 다시 실행한다. 다시 실행하면 **새로 생긴 것만 만든다.** 이미 있는 이슈의 본문을 고치거나, 목록에서 빠진 태스크의 이슈를 지우지는 않는다. 그런 변경은 GitHub 화면에서 직접 한다. 라벨의 색과 설명은 다시 실행할 때마다 스크립트에 정한 값으로 맞춰진다.

`tasks.csv` 를 Excel 로 고쳤다면 **CSV UTF-8(쉼표로 분리)** 형식으로 저장한다. 그냥 "CSV" 로 저장하면 한글 인코딩이 달라져, 스크립트가 UTF-8 로 다시 저장하라고 알리며 멈춘다. 칸의 규칙은 아래와 같다.

- 첫 줄의 `id`·`phase`·`title` 칸은 꼭 있어야 한다.
- `role` 칸의 값은 `npi.json` 의 역할 7종 가운데 하나여야 한다. 그 값으로 역할 라벨이 붙는다.
- 등급 칸 `NPI-A`·`NPI-B`·`NPI-C` 에는 `O`(그 등급에 깔린다), `인증시`(인증이 필요한 프로젝트에만 깔린다), 빈칸(깔리지 않는다) 중 하나를 쓴다.
- 그 밖에 더한 칸(예: 산출물, 기한)은 이슈 본문의 표에 그대로 실린다.

스크립트나 데이터를 고쳤다면 시험을 돌린다. `python -m pytest npi` 는 GitHub 를 부르지 않는다(pytest 가 없는 PC 에서는 `python npi\test_npi_github.py` 로 같은 시험이 돈다). 기준 자료(`reference/fitstack-npi-reference.md`, 저장소에 올리지 않는 파일)가 있는 컴퓨터에서는 `tasks.csv` 가 기준 자료의 34줄 표와, `task-library.csv` 가 83줄 목록과 한 칸씩 같은지도 함께 대조하고, 없는 컴퓨터에서는 그 두 시험만 건너뛴다.

## Claude 에게 맡길 수 있는 것

- "`1. Concept` 마일스톤 이슈들의 근거를 모아 Fitstack 게이트에 올릴 요약 초안을 만들어 줘"
- "이번 주 마일스톤별 진행을 세 줄로 요약해 줘"
