# 세션 보고 — Fitstack NPI 기준을 옮기고 처음 돌려 봤다 (2026-10-16)

> **결론:** 기준 자료(`reference/fitstack-npi-reference.md`)의 내용을 `npi/` 의 데이터 두 파일에 그대로 옮겼다. 옮긴 것은 표준 태스크 83개, 단계 5개, 마일스톤 태스크(★) 18개, Phase Review 규칙 3줄, 등급별 시작 단계 2개다. 시험 8개가 모두 통과했고, 그중 하나는 데이터를 기준 자료와 한 줄씩 대조한다. 미리 보기(`NPI-A`)는 빈 곳 경고 없이 라벨 2개, 마일스톤 5개, 이슈 83개를 만들 계획을 보였다.

## 옮긴 내용

단계와 태스크는 기준 자료의 순서와 문구 그대로다. **마일스톤 태스크(★)** 는 기준 자료가 단계 안에서 핵심으로 표시한 태스크이고, GitHub 의 "마일스톤"(단계를 담는 상자)과는 다른 것이다.

| 단계 | 태스크 번호 | 마일스톤 태스크(★) | 게이트 = Phase Review 이슈 |
|---|---|---|---|
| Concept | 1~6 (6개) | 1, 6 | [6] Concept Phase Review |
| Planning | 7~18 (12개) | 7, 8, 9, 17, 18 | [18] Planning Phase Review |
| Development | 19~53 (35개) | 19, 44, 51, 53 | [53] Development Phase Review |
| Release to Manufacturing | 54~72 (19개) | 57, 69, 70, 71, 72 | [72] Release to Manufacturing Review |
| Product Launch | 73~83 (11개) | 77, 83 | [83] Launch Product |

**Phase Review 규칙(`gate_rules`)** 은 기준 자료 머리말의 세 줄이다. 첫째, 단계는 5개이고 순서가 고정이다. 둘째, 각 단계의 마지막 ★ 태스크가 그 단계의 게이트다. 셋째, 등급에 따라 게이트 수가 바뀌므로 단계는 번호가 아니라 이름으로 식별한다.

**등급별 시작 단계(`grades`)** 는 두 개다.

| 등급 | 시작 단계 | 근거 |
|---|---|---|
| `NPI-A` | Concept | 기준 자료에는 없다. CEO 브리프의 "NPI-A · 게이트 5개"(게이트 5개는 다섯 단계 전부라는 뜻)와 성공 기준 v2 의 "등급 NPI-A" 를 근거로 했다 |
| `NPI-C` | Development | 기준 자료의 "C급은 Development 부터 시작"을 옮겼다. 이름 `NPI-C` 는 이 저장소의 `NPI-A` 표기에 맞춘 것이다 |

**기준 자료에 없던 것.** 아래 넷은 지어내지 않고 비워 두었다.

- **단계별 산출물 목록.** 기준 자료에는 태스크와 ★ 표시만 있다. ★ 태스크 대부분이 "Market Requirements Document Complete" 처럼 문서가 완성되는 시점이어서 산출물 구실을 하지만, 따로 정리된 산출물 목록은 없다.
- **단계별 통과 조건.** README 와 9/30 미팅 기록을 보면, Fitstack 의 Concept 게이트에는 통과 조건이 4건 있고 그중 하나가 "개발 목표·성공 기준 확정"이다. 그런데 기준 자료(Fitstack 태스크 템플릿을 발췌한 것)에는 이 조건들이 없다. 그래서 GitHub 의 Phase Review 체크리스트는 기준에 있는 ★ 태스크로 채웠고, Fitstack 게이트 화면의 통과 조건과는 아직 같지 않다.
- **태스크별 담당 역할.** `tasks.csv` 의 `role` 칸이 비어 있어서, `역할:` 라벨은 만들어지지 않는다.
- **B급의 시작 단계.**

**기준 자료에서 눈에 띈 것.** "EMS Readiness Review" 가 61번과 68번에 두 번 나온다. 기준 그대로 두 줄 모두 옮겼고, GitHub 에서는 이슈 제목 앞의 번호로 구분된다.

## 실행 결과 — 미리 보기

모두 기본 모드(미리 보기)로만 실행했다. 미리 보기는 GitHub 를 읽지도 쓰지도 않고, 실행할 `gh` 명령을 보여 주기만 한다. 결과 파일은 저장소 밖 임시 폴더에 두었다.

| 실행 | 결과 |
|---|---|
| `--grade NPI-A` | 라벨 2개, 마일스톤 5개(`1. Concept` 부터 `5. Product Launch` 까지), 이슈 83개. 빈 곳 경고가 없다. 그중 `Phase Review` 라벨이 붙는 것은 [6], [18], [53], [72], [83] 다섯 건이다 |
| `--grade NPI-C` | 라벨 2개, 마일스톤 3개(`3. Development` 부터), 이슈 65개 |
| `--grade NPI-B` (기준에 없는 등급) | "등급 'NPI-B' 이 grades 에 없다"를 알리고 실패(종료 코드 1)로 멈췄다. 실행을 거부하는 갈래가 실제로 동작한다 |

예를 들어 `[18] Planning Phase Review` 이슈의 본문은 세 묶음이다. 첫 묶음은 ★ 태스크 [7]·[8]·[9]·[17] 의 체크 칸, 둘째는 Phase Review 규칙 3줄, 셋째는 GitHub 에서 확인할 항목 4칸이다. 게이트 자신인 [18] 과 ★ 가 아닌 태스크는 체크 칸에 들어가지 않는다.

## 확인하지 못한 것

- **`gh` 의 실제 동작과 `--apply`.** 지시대로 실행하지 않았다.
- **이슈 양식(`.github/ISSUE_TEMPLATE/npi-task.yml`)이 YAML 로 읽히는지.** 이번에 바꾸지 않은 파일이다. 검사용 한 줄 실행이 이 세션에서 승인 대기로 막혔다. main 에 머지된 뒤 GitHub 의 New issue 화면에서 확인할 수 있다.
- **앞 세션의 독립 검토 결과.** 앞 세션 보고는 "다음 커밋에서 반영한다"고 적었지만 커밋으로 남지 않았다. 이번에는 그 대신 시험과 미리 보기를 실제로 실행해 확인했다.

## 남은 것 (요청 범위 안)

이번 요청은 커밋까지였다. 배포완료까지 남은 것은 아래 셋이다.

1. **PM 이 옮긴 내용을 기준 자료와 대조한다.** 로드맵 1단계의 마지막 손이다. 글자 단위 대조는 시험이 이미 했으므로, 사람은 위 "옮긴 내용" 표의 해석(★ 와 게이트, 등급)이 맞는지만 보면 된다.
2. **push 하고 PR 을 연다.** 지시가 있을 때 한다.
3. **머지한 뒤 PM 이 `--apply` 로 GitHub 에 깐다.** 순서는 [사용 가이드](how-to-work.md)에 있다.

## 참고 — 함께 발견한 것 (지시가 없으면 착수하지 않는다)

- **Fitstack 게이트의 통과 조건을 GitHub 심사에 넣을지 정해야 한다.** Concept 게이트의 통과 조건 4건이 기준 자료에 없다(위 "기준 자료에 없던 것"). 그 조건들을 기준 자료에 더해 주면 Phase Review 체크리스트에 한 묶음으로 넣을 수 있고, 데이터 칸 하나와 스크립트 몇 줄을 고치면 된다. 그대로 두면 로드맵 4단계(첫 Phase Review)에서 GitHub 와 Fitstack 의 체크 항목이 서로 다르게 보인다.
- **`.gitignore` 의 `reference/` 줄은 아직 커밋되지 않은 작업 트리 변경이라 이번 커밋에 넣지 않았다.** 이 줄을 그대로 커밋하면 `reference/` 폴더 전체가 무시된다. 그러면 앞으로 이 폴더에 새로 넣는 검토 자료(README 가 이 폴더를 "9/29 사전 검토 자료" 자리로 소개한다)도 조용히 빠진다. 이미 커밋된 6개 파일은 영향을 받지 않는다. 기준 자료 하나만 막으려면 `reference/fitstack-npi-reference.md` 한 줄이 더 좁다.
- **운영 틀 초안(브랜치 `docs/working-model`)과의 정리**는 앞 세션에서 넘어온 그대로 열려 있다(로드맵 "정해야 할 것").
