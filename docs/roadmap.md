# GitHub NPI 운영 로드맵

> **한 줄 요지:** Fitstack NPI 의 등급별 태스크(A 34 · B 16 · C 5)를 **태스크 하나에 GitHub 이슈 하나**로, 단계를 마일스톤으로 옮겨, **2026-10-19(월)부터 팀이 GitHub 하나만 열고 신규 Dock NPI 일을 하게** 한다. 단계 통과(Phase Review)와 게이트 승인은 Fitstack 에서만 한다. Fitstack 자동 동기화는 GitHub 운영으로 한 단계를 끝까지 돌려 본 뒤 **맨 마지막에** 붙인다. 그때까지는 사람이 근거와 PDF 를 Fitstack 게이트에 올려 맞춘다.

이 문서에 나오는 GitHub 용어를 먼저 풀어 둔다. **이슈**는 할 일 한 건을 담는 카드다. **마일스톤**은 이슈를 묶는 상자이며, 묶인 이슈 가운데 몇 건이 닫혔는지를 진행 막대로 보여 준다. **라벨**은 이슈에 붙이는 색깔 꼬리표로, 꼬리표별로 이슈를 걸러 볼 수 있다. Fitstack 의 무엇이 GitHub 의 어디로 가는지는 [사용 가이드](how-to-work.md)의 첫 표에, 도구별 역할과 정본 자리는 [운영 틀](working-model.md)에 있다.

## 지금 어디에 서 있나 (2026-10-16)

기본 세트를 Fitstack 의 등급별 34개 태스크로 바꿨고, 시험과 세 등급의 미리 보기를 실제로 돌려 통과했다. GitHub 에는 아직 아무것도 만들지 않았다.

- **옮긴 것:** 태스크 34개와 등급별 포함 여부, 담당 역할(`npi/tasks.csv`). 단계 5개(마지막 이름은 `Launch`), 등급마다 거치는 단계, 역할 7종(`npi/npi.json`). 원본은 Fitstack 의 `app/src/lib/projects/npi.ts` 이고, 기준 자료 `reference/fitstack-npi-reference.md` 를 거쳐 옮겼다. 기준 자료는 저장소에 올리지 않는다.
- **선택 라이브러리로 내린 것:** 같은 날 먼저 옮겼던 83개 태스크(Fitstack 의 옛 템플릿). Fitstack 에서도 등급 모델 뒤로는 자동으로 깔리지 않는 라이브러리라, `npi/task-library.csv` 에 두고 필요한 것만 이슈로 더한다. 83개를 옮겼던 때의 보고는 [세션 보고](session-summary.md)에 있다.
- **확인한 것:** 시험 8개가 통과했고, 그중 둘은 두 CSV 를 기준 자료와 한 칸씩 대조한다. 미리 보기는 빈 곳 경고 없이 `NPI-A` 라벨 8개·마일스톤 5개·이슈 34개, `NPI-B` 8·3·16, `NPI-C` 8·2·5 를 만들 계획을 보였다.

그래서 남은 선행 조건은 PM 이 옮긴 내용을 기준 자료와 대조하는 것, 그리고 이 브랜치를 PR 로 올려 머지하는 것(2단계)이다.

### 단계마다 조심할 것

- **1단계.** 옮기다가 내용을 지어내지 않도록 스크립트가 기준 숫자와 대조한다. 태스크가 34개가 아니거나, 등급별 수가 A 34 · B 16 · C 5 가 아니거나, 역할이 7종 밖이거나, 등급의 단계가 단계 목록에 없으면 실제 실행을 거부한다. 등급별 수는 인증이 필요한 기준이다. 3번 대상 제품 연결은 Fitstack 에서 "각 등급의 첫 게이트" 소속이라, 데이터에는 Concept 으로 적고 C 에서는 첫 단계인 Development 로 내려오게 했다.
- **2단계.** 실제 실행은 GitHub 에 이슈를 한꺼번에 만든다. `NPI-A` 면 34건이다. 그래서 실행 전에 PM 이 미리 보기를 훑어보고, 저장소 이름을 직접 적어 실행한다(`--apply GeonwooKim-fitogether/smart-dock-npi`). 다시 실행해도 이미 있는 것은 건너뛰므로, 중간에 끊기면 같은 명령을 다시 돌리면 된다. 이슈 양식은 main 에 머지된 뒤에야 GitHub 의 New issue 화면에 나타난다.
- **3단계.** git 을 몰라도 참여할 수 있게 한다. 팀원이 하는 일은 브라우저에서 내 이슈를 찾고, 댓글을 달고, 파일을 끌어다 놓고, 닫는 것이 전부다.
- **4단계.** 이 로드맵의 진짜 시험대다. GitHub 에서 닫힌 이슈의 근거를 Fitstack 게이트로 처음 옮기므로, 그 수고가 얼마인지 여기서 잰다. 그 수고가 6단계 설계의 입력이 된다.

## Fitstack 자동 동기화를 맨 뒤에 두는 이유

1. **무엇을 동기화할지는 한 번 돌려 봐야 안다.** 4단계에서 사람이 손으로 옮겨 보면 실제로 반복되는 수고가 드러나고, 자동화는 그것부터 없앤다. [운영 틀](working-model.md) 6절도 같은 순서를 적었다.
2. **Fitstack 에 쓰는 일은 실제 운영 데이터베이스를 바꾸는 일이다.** 회사 규칙상 운영 데이터베이스 쓰기는 사람이 그 내용을 보고 승인한 뒤에만 할 수 있고, 먼저 비운영 환경에서 시험해야 한다([데이터베이스 쓰기 규칙](../.claude/rules/db-write-permission.md), [환경 분리 규칙](../.claude/rules/environment-separation.md)).
3. **자동화에는 권한과 비용이 따른다.** GitHub 와 Fitstack 을 잇는 토큰이나 앱 권한은 보안 결정이고, 주기적으로 도는 자동 작업은 유료인 GitHub Actions 사용 시간을 쓴다. 둘 다 사람이 정할 일이다([에스컬레이션 규칙](../.claude/rules/escalation.md) §2).

## 6단계의 윤곽 (기획만 해 두고, 아직 만들지 않는다)

1. **연결 열쇠는 지금 깔아 둔다.** 이슈 제목 앞의 `[태스크 번호]` 는 Fitstack NPI 태스크 세트의 순번(1~34)이다. 등급이 달라도 같은 태스크는 같은 번호다. 단계는 마일스톤 이름 속의 단계명으로 짝짓는다. Fitstack 에서는 등급에 따라 게이트 순번이 달라져(C 에서는 Development 가 첫 게이트다) 번호로는 짝지을 수 없기 때문이다. 마일스톤 이름 앞의 번호는 목록을 단계 순서대로 세우기 위한 고정 순번일 뿐이다. 처음부터 이 형식으로 만들어 두면, 나중에 둘을 짝짓는 표를 따로 만들 필요가 없다.
2. **읽기 전용 내보내기부터 한다.** GitHub 의 단계·태스크 상태를 표 하나로 뽑아 사람이 Fitstack 과 대조한다. 아무것도 쓰지 않으므로 위험이 없고, 4단계의 손 작업도 줄어든다.
3. **비운영 환경에서 쓰기를 시험한다.** Fitstack 의 개발·스테이징 환경에 먼저 반영해 본다.
4. **운영 반영은 결정 카드로 승인받은 뒤에 한다.** 그 뒤에도 Phase Review 승인과 게이트 확정은 Fitstack 에서 사람이 한다. 자동화는 근거 링크와 초안을 채우는 데까지만 맡는다.
